# Karaoke Platform 0.9.1

A consolidation release. 0.9.0 shipped the AI DJ; this one finishes the
**SQLite to PostgreSQL migration** that was left half-applied around it, adds
**chord-level harmonic analysis**, and carves out a **shareable demo library**
so the platform can be run by someone who does not have this machine's music.

## Harmonic analysis below the key

- **Chord detection (`chords.py`)**: Key windows average over cadences, so they
  cannot see jazz — a ii-V-I is what makes a cadence rather than a modulation.
  Measured, Ella Fitzgerald singing Cole Porter scored 76% tonal stability
  against 77% for the Red Hot Chili Peppers, and 2.1 distinct key centres
  against 2.2. At the level of key, they are the same music. Chord detection
  works at four frames a second instead — CQT chroma against 24 triad templates,
  runs collapsed into chords, root motion recorded as a key-invariant histogram.
  Harmonic vocabulary separates them, across 489 tracks:

  | | | | |
  |---|---|---|---|
  | Bill Evans Trio | 22.5 | corpus mean | 16.4 |
  | Al Di Meola | 21.3 | B.B. King | 15.5 |
  | Nina Simone | 18.2 | Ween | 11.4 |

  B.B. King at 15.5 is the check that matters: blues sits next to jazz but is
  harmonically simple, and the measure declines to call it complex.

- **Percussive/harmonic separation is off by default.** It cleans the chroma but
  was 95% of the runtime — 37.0s against 1.7s for the CQT itself, which over a
  library is a day against an hour. Pass `harmonic=True` when the precision is
  worth it.

- **Key movement tracked and backed up**, with chord fields joining the
  progression document — key movement and chord movement describe the same
  track. `ensure_chord_fields` adds the mapping to indexes created before the
  fields existed, since a `knn_vector` cannot arrive by dynamic mapping.

- **`circle-of-fifths` renamed to `fifth-related`**, and the fifth-related form
  was then dropped entirely: it fired on roughly 1.3% of tracks but at the same
  rate for Ella as for everything else, so it measured tonal travel, not idiom.
  The old name promised genre detection the key level cannot deliver.

## Scanning and identification

- **Parallel scan workers**, each capped to four threads. numpy and librosa
  thread internally, and six workers each grabbing 24 cores is slower than six
  taking four.
- **Control over how much audio is sampled**: `embed_audio` gains `max_windows`
  and `full`. Six ten-second windows cover about a quarter of a four-minute
  track — ample for timbre — but a caller wanting the whole body can now tile it
  end to end. Both are rebuild-level decisions: vectors built under different
  windowing are not comparable.
- **`songrec` was never fingerprinting anything.** `recognize` takes the input
  file positionally; the file fingerprinter passed its sliced wav to `-d`
  (`--audio-device`), so songrec treated the path as a microphone name and
  printed its device list to stdout. `json.loads` failed on that and a bare
  `except` returned `None` — exiting 0 throughout, so the result was
  indistinguishable from "no match" and whole-library scans reported
  `fingerprinted: 0` without ever erroring. Fingerprinting is the third fallback
  in `folder_scan`, so with it dead every poorly tagged file fell through to
  filename guessing. That is where `Nuevo interprete - 06 - Full Monty.mp3` came
  from. Californication, Under the Bridge and Dolphin Dance now identify
  correctly, the last by title alone.
- **CLAP embeddings keep their vector** and no longer sample the intro.

## Recordings

- **Analysing a session no longer prunes the others.** The retention sweep ran
  as a side effect of `analyse` unless `--keep` was passed, so decompiling one
  session could silently delete unrelated older audio past the seven-day or
  eleven-gigabyte cap. The recording being analysed was never at risk, which
  made it harder to notice: the session in front of you survived while others
  quietly went. A radio broadcast cannot be recaptured, so retention is now
  explicit — `--prune-after` on the CLI, `prune_after` on the API. `--keep` and
  `keep=` stay accepted and do nothing, so saved commands keep working.

## Demo library

- **`demo/karaoke-demo.db` and `demo/karaoke-demo.sql`** — 309 radio-derived
  tracks, 232 with lyrics, plus analysis, genre and tone labels, cover art and
  sync offsets. Two formats: SQLite for the pre-migration schema, and data-only
  Postgres INSERTs for after. Neither carries a schema; the `.sql` expects a
  database already built from `POSTGRES_DDL` in
  `scripts/migrate_sqlite_to_postgres.py`, which stays the single schema
  authority. Regenerate with `scripts/make_demo_db.py`.
- Withheld deliberately: listening history, recordings referencing audio that is
  not shipped, working state, and the relay's own events and outbox. `local`
  sources are dropped too — they are absolute paths into this machine's YouTube
  cache, and the audio does not travel with them.

## Migration aftermath

The cutover to psycopg was unconditional, but several call sites were not
brought along. Each surfaced as its own crash:

- **`artist_genres` lost a key column.** `POSTGRES_DDL` declared
  `PRIMARY KEY (artist_normalized, genre)` while SQLite and the live database
  both key on `(artist_normalized, genre, broad_genre)`. One genre maps to
  several broad genres, so the narrowed key could not hold the data. It also
  silently disabled genre learning: `artist_classifier` upserts with
  `ON CONFLICT(artist_normalized, genre, broad_genre)`, which needs a unique
  constraint over exactly those three columns, and the call site swallowed the
  resulting exception into a log line.
- **The cluster had no Postgres.** The API image installed only the web stack,
  so the pod died at import with `ModuleNotFoundError`, and the kind manifests
  still assumed a SQLite file on the data volume. Adds the driver to the image
  plus a Postgres deployment, service and volume, with `KARAOKE_PG_URL` pointing
  at it. The schema is not duplicated — CI extracts `POSTGRES_DDL` textually and
  mounts it as a ConfigMap on the Postgres entrypoint.
- **`recording-analyse` ran in the audio venv**, which is a DSP-only sidecar
  with no database driver, so it died at import. Routing a database entry point
  through that interpreter was the mistake; installing psycopg there would have
  fixed the symptom and broken the isolation the sidecar exists for.
- **`row[0]` on a psycopg dict row** raised `KeyError: 0` in `folder_scan`, so
  the YouTube id fallback crashed on every cache file — a scan reported seen
  102, processed 0, errors 102. Same root cause as the `?` placeholders
  previously found in `scripts/db_cleanup.py`.

A sweep for positional row access, and for interpreters that import
`localcache`, would likely find more.

## DJ booth

## Documentation

- Topology docs now match the deployed reality, and document what survives a
  reboot.
- `karaoke.chords` and `karaoke.key_progression` are documented in the API
  reference; the harmony work had added them without touching `docs/api.md`.

  venv.

## Verification

- `make test` — **1768 passed, 5 skipped**, against a real PostgreSQL.
- Demo dump loaded into a throwaway Postgres schema built from `POSTGRES_DDL`:
  all ten tables arrive at their expected counts, and the serial sequences land
  past the copied ids.
- Chord measure validated across 489 tracks, with B.B. King as the negative
  control against the jazz cluster.
